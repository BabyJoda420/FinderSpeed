# BUG-001: semi-transparent panel and a full-width band (apollo): FINAL

**Status:**
- Fixes (a)–(e) and the diagnostic log are implemented and verified on this Mac (1x).
- `swift build` (debug and release) is clean, and `swift test` passes 48/48.
- The symptom mechanism is proven by fault injection.
- The user's own MacBook (Retina) still has to confirm it. The diagnostic build's log tells us within one slow move (see "For the diag build").

## Root cause

### Proven: AX trouble made the panel flap and freeze

When Finder answered AX slowly or with errors, the panel flapped and its fade froze. Two flaws in the Window module combined:

1. **Any failed AX read counted as "window gone".** In the old `readInfo`, a timeout (`kAXErrorCannotComplete`) on the role read followed by a failed frame read returned nil. The observer then:
   - untracked the window and emitted `.disappeared`, so the panel faded out and was ordered out;
   - re-detected the window on the next good scan and emitted `.appeared`, so the panel faded in again.

   In the same failures, `isActive` read as false, which flipped the chrome between its key and non-key variants and re-rendered it.
2. **All AX calls ran synchronously on the main thread.** That is about 3–30 calls per read, each able to wait up to the AX timeout. Window elements don't even inherit the app element's 0.5 s timeout, so they used the 6 s default. The same main thread drives:
   - AppKit's window-alpha fade (`NSAnimationContext` + `animator().alphaValue`);
   - the layout and display pass that applies `NSVisualEffectView.maskImage`.

A slow "Moving 28 items" to a USB HDD, running for minutes, is exactly when Finder answers AX slowly.

### Evidence: fault injection

`FINDERSPEED_SIMULATE_AX="delay=0.3,fail=0.3"` makes every AX read sleep 0.3 s and fail 30% of the time, like a busy Finder. The run is `spikes/window/bug001/simulate.sh` during a 40,000-file copy, with the release build in fallback mode, sampling CGWindowList every 100 ms for 60 s.

With different timing it freezes at an intermediate alpha. | the fade is render-server driven, and the model value is final immediately |

**Proven by probes:** a window at partial alpha shows exactly the user's "sharp, unblurred, semi-transparent" look (`bug001/matprobe2.swift`: alpha 0.6 over red stripes gives (127,43,49), with the stripes visible).

### The full-width band: not reproduced on this Mac, made structurally impossible

**Ruled out by probes:**
- the inactive material (opaque in every state, mask applied: `matprobe.swift`);
- window alpha < 1 breaking the mask (the mask still applies: `matprobe2.swift`);
- a 1x mask on a 2x backing (`maskImage` follows its point size at pixel scale 0.5, 1 and 2, covering exactly 1776 of 12000 px each time: `maskscale.swift`).

**Remaining candidate:** a starved layout pass leaving a freshly set `maskImage` unapplied while the chrome was re-rendered by the active-state flapping (unverified). Fix (d) makes the full-width band impossible whatever the cause.

## Fixes (all in `Sources/FinderSpeed/Window/`)

| | Change |
|---|---|
| **(a)** | `FinderProgressWindowObserver`: a read returns `.gone` **only** for `kAXErrorInvalidUIElement`. Besides that, only a destroyed notification for our element, or a **successful** window list without it (`verifyTracked`, 1 Hz), means gone. Any other failure means `.failed`: keep the last info and emit nothing. Individual fields that fail keep their previous values: rows (`readRows` returns nil instead of partial rows), `AXMain`, minimized. |
| **(b)** | Every AX read and every notification registration runs on a serial `axQueue`. Results are applied on the main thread, reads are coalesced (one in flight plus one pending), and stale results are dropped by generation. The AX callbacks only schedule work. The AX messaging timeout is 1.0 s, set process-wide, so derived elements no longer wait the 6 s default. |
| **(c)** | `SpeedPanelController`: the window `alphaValue` is fixed at 1 and never animated. The fade is a Core Animation animation of the root layers' opacity: the **model value is set to its final value immediately**, and the animation runs in the render server. `orderOut` happens after the fade through `asyncAfter`. If the main thread is late, the panel is already invisible. Before showing, frames, masks and content are committed (`layoutSubtreeIfNeeded`, `displayIfNeeded`). |
| **(d)** | The band is three `FillPatch` views: the left corner (24×20 pt, masked), the right corner (24×20 pt, masked) and the 4 pt strip (unmasked). The body is one masked patch. **Even with no mask at all, nothing above the 4 pt strip can be painted wider than the two 24 pt corner blocks.** Each patch holds the material and the sampled solid fill. The material always stays `.active`; Finder's own background measured the same in both states. |
| **(e)** | `WindowChromeRenderer.render(…, scale:)`: the chrome is evaluated at 1 pt per pixel from the measured tables and replicated to `scale × scale` pixels per point. It is then shown with `contentsScale = scale` and mask `NSImage`s sized in points. The scale is that of the screen Finder's window is on. It re-renders on `NSWindow.didChangeBackingPropertiesNotification`, `didChangeScreenNotification` and `NSApplication.didChangeScreenParametersNotification`. **Notch:** no geometry change is needed, because AX and AppKit both use the full screen frame. The insets are logged. |
| **Diagnostics** | `WindowDiagnostics`: on with `FINDERSPEED_DEBUG_WINDOW=1`, or with the `FinderSpeedDebugWindow` default, or **by default when the bundle version contains "diag"** (e.g. 0.1.1-diag). A diag build can still be switched off with `defaults write <bundle-id> FinderSpeedDebugWindow -bool NO`. It writes `~/Library/Logs/FinderSpeed.log` (restarted above 5 MB), and the header includes the version. |
| **Test hooks** | `FINDERSPEED_SIMULATE_AX="delay=…,fail=…"` (fault injection), `FINDERSPEED_NO_SAMPLE=1` (force the material fallback). |

## For the diag build (0.1.1-diag) on the MacBook

Ask the user to run a slow move and send `~/Library/Logs/FinderSpeed.log` plus a screenshot. Things to check:

- **`env` lines:** the scale (expect `scale 2.0`), the colour space, and `safeAreaInsets` / `auxTopLeft` for the notch.
- **`ax/bg` lines:** slow or failing AX calls with their durations and error codes (-25204 = cannotComplete). Many of these confirm the root cause.
- **`observer` lines:** `read failed (…), keeping last info` (the fix working), and whether any `event disappeared` happens while the window is still on screen. There should be none.
- **`panel` lines:**
  - `rendered chrome 404xH @2x`: confirms the Retina path;
  - `show` / `hide` should be once per copy;
  - the 1 s `tick` lines: `opacity`, `presented` and `winAlpha` should all be 1.00 while shown.
